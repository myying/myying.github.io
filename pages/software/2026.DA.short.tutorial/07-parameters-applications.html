Parameter estimation

Every widget so far has estimated state — a temperature field, a storm's position. The same machinery estimates parameters too, just by putting them in the state vector: this is the same cycling, 3x3 nine-station storm-tracking EnKF as Chapter 3, with the same perfectly deterministic truth (constant, exactly known velocity, no jitter), augmented with the one thing that widget assumed was known outright — the storm's velocity. State = (cx, cy, u, v). Velocity has no dynamics of its own — the forecast step just carries each member's own guess forward unchanged — so the only way it ever moves is through the analysis, via whatever cross-covariance builds up between "my velocity" and "the temperature I'd see at each station". Nothing here ever observes velocity directly. There's no bias-correcting inflation control: velocity here is a genuinely static, unknown quantity, so letting its spread shrink as evidence accumulates is mostly the right behavior. But not entirely: a small "background" perturbation is still applied to velocity after every analysis (0.05 km/cycle). Without it, once velocity spread fully collapses the Kalman gain vanishes too, and an early unlucky sample can occasionally leave the estimate permanently stuck away from the truth with nothing left to correct it — tried and confirmed numerically. The small background nudge keeps a sliver of spread alive so that can't happen, without being large enough to stop the estimate from actually converging. Position gets no perturbation at all — unlike Chapter 4, it doesn't need one here: with velocity now being estimated, position tracking relies entirely on each member's own estimated velocity to correct its trajectory (confirmed numerically: adding position perturbation back didn't meaningfully help, so it's left out). An Estimation: on/off toggle lets you freeze velocity at whatever it currently is — no analysis update, no perturbation — to see what the widget looks like without any parameter estimation happening at all.

Try it: the members start with a rough first guess, biased a bit low (mean speed 4 km/cycle, true speed ~9.5), plus spread wider than the guess. Hit run and watch the "drift speed" panel: dozens of thin cyan member lines start scattered around that low first guess, then narrow together into a cluster that climbs toward the dashed true-speed line — the thicker blue ensemble-mean line runs through the middle of that cluster. Then try toggling Estimation off mid-run: the cluster stops narrowing and just drifts along at whatever speed it was frozen at.

Reading the panels

1 · The storm track — the map is identical to Chapter 4's: member dots, the ensemble mean, and the truth's actual track and 4 K footprint. Unlike Chapter 4, the member cluster here isn't held open by any position perturbation — its spread comes entirely from how much the members still disagree about the storm's velocity. The velocity estimate itself isn't drawn on this map — see the drift-speed panel for that — but it's what pulls the member dots into closer and closer agreement with the truth as observations accumulate, because a member whose velocity has been carrying it toward the observed temperatures is, on average, a member whose velocity estimate deserves to survive.

2 · Drift speed — the most direct view of convergence: every member's own estimated speed |(u, v)| is a thin cyan line, so the whole ensemble reads as a cluster of trajectories, with a thicker blue line for the ensemble mean running through its middle. They start clustered around the low first guess and, as observations accumulate, climb and narrow sharply toward the dashed true-speed line — with no perturbation reinflating velocity, the cluster genuinely collapses onto a single answer rather than lingering as a visible spread. Toggle Estimation off and the cluster freezes wherever it was instead of continuing to narrow.

3 · Ensemble spread vs. rms error — the same position spread-vs-error pattern as Chapters 3 and 4: spread (blue) and rms error (red), both for the storm's position, not velocity — velocity's own convergence already has a clearer picture in panel 2. If they track each other reasonably well, the filter is honest about its own uncertainty in where the storm is, even while it's still learning how fast it moves.

This is state augmentation, in full: any quantity you can write a forecast step (even a trivial "unchanged") and an observation operator for can ride along in the state vector and get estimated the same way — model parameters, bias corrections, boundary forcing. It is also the same idea behind the NEDAS tutorials' real applications, and behind the question that opened this whole series: how much can you actually know about a system you can only watch through a handful of point observations?

→ Evensen et al., Data Assimilation Fundamentals (2022), Ch 19–23 — parameter estimation and examples.
